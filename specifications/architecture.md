# Architecture

## Current engine

CoCreateDB is a client-server database engine for building distributed databases. The same asynchronous CRUD engine runs locally in a browser client or a Node server. `await createDB(server, options)` and `await createDB.init(server, options)` expose asynchronous `send(request)` and `config`. Initialization opens the runtime's storage adapter and restores its configuration and indexes before resolving. A standalone instance requires no server. Primary server instances execute local CRUD; Node workers use the supplied `forward(request)` adapter. Explicit primary status takes precedence. No IPC protocol is embedded.

Internally one UUID-keyed leaf Map, one key/type tree catalog and a root manager maintain live data. Index entries reference leaves directly. Offloaded terminal branches are stored separately from leaves; the root/parent branch catalog is not yet restored on restart. Configuration defines allowed hierarchy and structural identities; it is not a data snapshot.

## Local residency and defaults

The default mode is `adaptive`; the default acknowledgement is `memory`. Adaptive keeps a Hot working set in memory and uses Warm local disk for write-through, recovery and weighted eviction. The default requested memory budget is 25% of total system memory, capped by memory available at startup. It is a soft DB-residency target, not a hard process-memory cap. Disk-first remains an explicit mitigation mode and is also used temporarily by adaptive handling at high pressure. Disk-cache starts with a cleared DB-managed local base.

The package has one `src/index.js` entry and one composition lifecycle for both environments. It wires Tree, CRUD, query planning, Persistence and disk. The disk module dynamically loads the client adapter or server adapter; Tree and CRUD do not import platform APIs. The server adapter uses the filesystem and defaults to `~/.cocreate/db`; adaptive Hot/Warm residency is the default. The client adapter uses OPFS and disk-first request processing; its default base is the relative OPFS directory `CoCreateDB/`, and a configured `directory` is interpreted as a relative path beneath the origin-private root. Both adapters use `config.json`, `branches/` and `leaves/`. OPFS is scoped to the browser origin, requires a secure context and is subject to browser quota management. Node filesystem imports are confined to `src/disk/server.js` and dynamically loaded only by the server runtime.

Successful `object.create`, `object.update`, and `object.delete` requests in adaptive mode acknowledge after their in-memory leaf-map mutation. Create assigns or accepts a UUID and stores the leaf; update mutates the leaf; delete removes it from the resident map and records a pending local deletion. Supplied-UUID create, cold-leaf hydration, and query matching can require work before the mutation itself is applied.

After acknowledgement, Warm local work proceeds in order: persist changed or deleted leaves, reconcile the derived in-memory indexes, then persist changed index branches and config. `flushIndex()` waits for index reconciliation; `flushDisk()` waits for local disk work. Disk-first uses the same memory acknowledgement and local flush path, then releases processed leaves and resident index branches while retaining their disk files. Memory acknowledgement means the mutation was accepted in this DB's memory; it does not certify that this server's disk write has completed. Client copies and peer delivery may add system-level redundancy, but are owned by the surrounding distributed application. Neither acknowledgement is a multi-object transaction. The replaceable `persistence.send` callback, server-side workflow and `db.persist()` are a separate external-persistence process; the pending journal is not the local durability boundary. The separate Persistence Tree and Cold archives remain outside the implemented engine.

## Integration boundary

CoCreateDB supplies the local database at either end of a client-server application. CoCreate CRUD routes authorized requests to an instance, then invokes a configurable workflow with the request and response. Workflow/AST can acquire missing data and schedule or await persistence orchestration. Socket, IPC and Mesh own awareness, client-server delivery and peer communication. These surrounding layers use database instances to form a distributed database; the DB package itself does not open connections, discover peers, select recipients or replicate changes automatically. Server persistence defaults to the named DB workflow; a host may replace `db.persistence.send` directly.

Local success does not establish global completeness or external durability. DB eviction mitigates its own Hot/Warm residency; it cannot protect total server RSS from unbounded incoming requests or server-side queues. Process-level OOM protection belongs to server telemetry and network traffic management, including admission control, draining and client backoff. External integration must preserve identity, authorization and operation context. See [CRUD](crud.md), [indexes](indexes.md), [persistence](persistence.md) and [awareness](awareness.md).
